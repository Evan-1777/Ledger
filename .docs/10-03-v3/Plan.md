## 1. 背景与目标

当前记账系统已交付资产与负债渠道管理及宏观资产看板，但交易录入体系仍局限于传统的二元收支模型（支出与收入）。在实际使用中，信用卡还款、债务偿${还}是高频刚需业务。本次计划将“还款”作为一等公民引入主系统，打通负债与资产、交易流水与统计看板的物理闭环：

- **三位一体交易录入与编辑闭环**：记账模态窗支持「支出 / 收入 / 还款」三段式平滑切换；新建与更新（PUT）全链路闭环，编辑模式下锁定交易类型，杜绝跨类型状态错乱；
- **分类锁定与系统内置契约（ID 级根因防护）**：还款场景强制锁定消费类型选择；在热迁移阶段注入单系统级分类「债务偿还」及单标签「负债还款」，并将 ID 持久化至 `system_meta`，删除与改名端点基于 ID 严格拦截；
- **双边资产负债平衡**：支持指定还入负债渠道与转出资产渠道，使还款后净资产严格守恒；
- **损益统计与筛选链路防污染隔离**：常规收支统计、月度趋势、储蓄率等看板严格排除还款数据；修正服务端 `?type=income` 及前端日分组小计，杜绝还款混入生活收入；
- **流水多维筛选与 Fluent 2 视觉自洽**：底部筛选胶囊扩展为 4 档位，流水卡片清晰呈现资金流转路径。

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 交易类型建模 | 显式增加 `type` 列 (`expense`/`income`/`repayment`) | 概念清晰、语义对称，便于后续扩展与 SQL 简单直观过滤 | 沿用金额正负推断（无法区分收入与还款，逻辑混乱） |
| 渠道扣减机制 | 引入可选 `source_payment_method_id`（转出资产渠道） | 既满足用户单选负债渠道直觉，又能严谨维护资产负债会计守恒 | 纯单边记账（导致总资产不变、负债减少、净资产凭空增加） |
| 系统分类与防护 | 注入单分类单标签，ID 存入 `system_meta`，按 ID 守卫 | 根因级解决改名击穿与删除问题，消除冗余死数据标签 | 按名称字符串匹配（可被改名绕过导致回填失效） |
| 种子注入时机 | 挂载于 `seed_initialized` 早退检查之前 | 确保已初始化过的老库升级时同样能注入系统分类 | 放在老库早退之后（老数据库升级后还款功能全链路报废） |
| 更新路径（PUT）契约 | 请求结构补齐 `type` 与 `source_pm_id`，更新语句落盘 | 保证编辑修改功能完整可用，支持修改渠道与金额 | 忽略更新路径或禁止编辑还款（功能残缺，体验断裂） |
| 报表与筛选隔离 | 统计与 `?type=income` 及日分组小计全面排除还款 | 还款属于资产负债转移而非经营收入，杜绝任何层级的报表与小计污染 | 仅在宏观统计过滤（导致流水单日收入与收入筛选被污染） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 老数据库升级后历史交易缺少 `type` 字段 | 🟡 中 | 探针热迁移时基于 `amount_cents` 符号进行历史数据原子补齐 |
| 用户无负债渠道时误触还款 | 🟢 低 | 前端判断负债渠道数量为 0 时给出温和置灰引导去设置页添加 |
| 负债渠道还款产生溢缴款（欠款为负） | 🟡 中 | 现有 clamp（`stats.go:359-370`）已能自洽约束在授信额度本身，净资产数学公式守恒 |
| 编辑已存在账单跨类型切换引发脏数据 | 🟡 中 | `RecordModal` 在编辑模式下锁定类型滑块，只允许在同类型下修改金额、备注与渠道 |

## 6. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估本阶段委托需求：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|

| Phase 3：前端记账模态窗 | 强（涉及 Fluent 2 滑块动效与表单交互约束） | 无（依赖 Phase 2 接口） | 主线 | 需细致打磨锁定状态、编辑态约束与渠道联动逻辑 |

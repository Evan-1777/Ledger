## 1. 背景与目标

当前记账系统仅具备单一维度的消费与收入流水记录，渠道（支付途径）仅作为普通文本标识附着在流水上，存在以下核心局限：
1. **缺乏资金存量感知**：无法追踪各个银行卡、微信零钱或支付宝账户中真实留存的可用金额，统计界面无法展示渠道剩余金额与整体资产总额。
2. **缺乏负债渠道管理**：无法建立信用卡、花呗、白条等负债账户，无法设置信用额度、初始待还款项以及追踪当前欠款敞口。
3. **缺少顶层财务健康度量**：缺乏“净资产（总资产 - 总负债）”这一衡量财务现状的核心宏观指标。

本次演进目标：
- 在数据库层将支付途径升级为一等公民渠道账户系统，统一支持资产渠道与负债渠道，支持初始底账与授信额度配置，且对已有数据老库实现零中断平滑热迁移；
- 扩展后端渠道管理接口与多维资产统计汇总接口，基于整数分代数模型精准计算各渠道实时结余、当前欠款、剩余额度与全盘资产总额；
- 在基础设置中提供清晰美观的资产与负债渠道分段管理界面，支持新增负债渠道、配置额度与底账，延续轻量内联交互；
- 在统计看板中引入资产与负债全局资产看板，展示净资产、总资产、总负债三核 KPI，以及各资产渠道剩余金额与负债渠道额度占用，严格遵循无噪原则。

## 2. 阶段划分

### Phase 1：数据库表结构扩展与老库平滑热迁移

| 项目 | 内容 |
|------|------|
| **输入** | 现有数据库初始化模块及单元测试 |
| **输出** | 渠道账户扩展字段（渠道类型、初始底账分、信用额度分）；基于列探针的幂等增量迁移逻辑；老库升级与约束单测 |
| **验收标准** | 全新数据库建表具备完整新字段；已有老数据库在启动时自动平滑增量补齐缺失列，历史渠道默认安全纳管为资产类型且初始底账为 0；数据库单测 100% 通过 |

### Phase 2：后端渠道业务扩展与多维资产统计引擎

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 数据层扩展、现有设置与统计服务模块 |
| **输出** | 渠道管理增删改查接口适配（支持类型、初始底账与额度读写）；多维资产与负债统计计算引擎（资产渠道结余、负债欠款、剩余额度、净资产计算） |
| **验收标准** | 渠道创建与更新可正确保存资产/负债属性；统计汇总接口返回完整的资产与负债概览；被流水引用的渠道删除严格返回 409 拦截；后端集成测试全绿 |

### Phase 3：前端设置页渠道工作台与新增负债渠道

| 项目 | 内容 |
|------|------|
| **输入** | Phase 2 接口定义、现有设置页组件与应用状态总线 |
| **输出** | 设置页渠道管理重构（资产渠道与负债渠道双分段并列）；支持新增负债渠道的轻量内联表单（录入名称、初始欠款与可选额度）；渠道编辑与删除守卫 |
| **验收标准** | 用户可清晰切换并查看资产渠道与负债渠道；可成功添加并编辑负债渠道属性；操作失败（如重名、409 冲突）呈现友好 Toast 反馈；无解释性冗余文案 |

### Phase 4：前端统计看板资产与负债总览及全量回归

| 项目 | 内容 |
|------|------|
| **输入** | Phase 2 统计接口、现有统计页组件与 Fluent 2 视觉令牌 |
| **输出** | 统计页顶部资产总览看板（净资产、总资产、总负债 KPI 卡片）；各资产渠道剩余金额卡片簇；各负债渠道欠款与剩余可用额度微进度条；全流程自动化测试 |
| **验收标准** | 统计页即时准确呈现资产与负债宏观指标及微观渠道结余；等宽数字排版无抖动；桌面端与移动端响应式自适应良好；`make test` 与 `make build` 100% 通过 |

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 账户体系模型 | 统一渠道扩展模型（在原有支付途径表增量扩充 `type`、`initial_balance_cents`、`credit_limit_cents`） | 结构归位与最短有效差分：避免新建一套重复冗余的“账户表”导致流水外键大拆大改，直接将既有途径晋升为具备完整财务属性的渠道账户 | 另立新表（将流水与设置割裂为两套异构模型，极度增加系统复杂性） |
| 存量金额计算方式 | 初始底账 + 符号整数分交易流代数累加 | 杜绝浮点漂移，保持与现有 transactions 核心模型 100% 对称；资产与负债公式完全统一，无需分支特判 | 维护独立的余额快照镜像表（存在数据同步竞态风险与双源不一致隐患） |
| 数据库热升级策略 | `PRAGMA table_info` 列探测 + 动态幂等 `ALTER TABLE ADD COLUMN`，执行点置于 `seed_initialized` 检查前 | 纯 Go SQLite 原生兼容性最佳，无需外部迁移工具或框架依赖；前置于早退判断确保已初始化的生产老库无条件补齐新字段 | 破坏性删库重建（丢失历史记账数据，完全不可接受） |
| 渠道类型翻转策略 | 显式允许用户在更新时调整 `type`，语义由用户自担 | 遵循个人工具轻量自决原则，避免引入复杂的跨表级联锁定逻辑或不可逆约束 | 冻结修改（若用户误选类型则无法纠正，必须删库或直接操作数据库） |
| 前端视觉排版 | Microsoft Fluent 2 规范、四层 Z 轴与等宽数字 `tabular-nums` | 对齐既有项目设计语言，层次分明、微阴影、浅边框，数据对比一目了然 | 扁平粗糙色块堆砌（违背项目设计规范与视觉质感要求） |
| 界面文案与交互原则 | 成品级表面、无解释性冗余文本、轻量内联展开录入 | 遵循 `production-frontend`，开发者作为用户已知入口与含义，界面无需说教；内联表单避免遮盖视图 | 大面积弹窗与新手引导教程（增加认知干扰与界面噪声） |

## 4. 风险清单与缓解措施

| 风险 | 等级 | 缓解与闭环措施 |
|------|------|----------------|
| 老版本数据库升级时，因缺失新字段导致查询或插入失败 | 🔴 高 | 在数据库连接初始化阶段执行探测式事务热迁移，历史数据默认置为 `asset` 且底账为 0，编写专门的老库升级单元测试用例闭环验证 |
| 负债渠道支出与收入代数符号混淆导致欠款计算错误 | 🟡 中 | 明确符号代数公理：负债渠道消费支出为负数，还款为正数，当前欠款公式为 `initial_debt - SUM(amount_cents)`，并在单元测试中覆盖正负交易组合 |
| 删除已有交易记录的渠道导致外键孤立或计算失真 | 🟡 中 | 后端服务层严格保留并在事务中执行 `SELECT COUNT(1) FROM transactions WHERE payment_method_id = ?` 拦截，引用存在时返回 409 Conflict |
| 额度超额或净资产为负引发界面进度条溢出或样式错乱 | 🟢 低 | 前端额度占用条采用 `Math.min(usage_rate, 100)%` 防溢出；净资产为负时采用柔和警示色并显式保留负号与格式化数字 |

## 6. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估委托需求：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：数据库扩展与热迁移 | 强（涉及 SQLite 连接、DDL 探测、事务与测试断言） | 无（系统底层基石） | 主线 | 差分小且为核心基础设施，主线直接实现避免上下文损耗 |
| Phase 2：后端接口与统计引擎 | 强（涉及数据计算链路、模型映射与集成测试） | 无（依赖 Phase 1 结构） | 主线 | 涉及核心数学与代数符号约定，主线把控保证逻辑严谨 |
| Phase 3：设置页渠道管理重构 | 强（涉及设置页组件树、SSOT 状态派生与内联表单） | 无（前端基础配置） | 主线 | 与既有 SettingsPage 交互深度耦合，主线就地重构最高效 |
| Phase 4：统计看板总览与全量回归 | 强（涉及 Fluent 2 视觉令牌、图表适配与全量集成测试） | 低（串行验收链路） | 主线 | 包含最终编译与端到端回归验收，主线闭环保证交付质量 |

> **协同结论**：全链路围绕资产与负债统一模型紧密相扣，跨模块修改精准聚焦，无独立耗时的大型外围分支，全量保留主线高效推进。

## 1. 背景与目标

### 现状问题（Explore 结论）

账目流水主页是全局 P0 主画布，承载最高频的「查账 / 对账」作业。现状视觉存在四类结构性问题：

| 问题 | 现状 | 影响 |
|------|------|------|
| **卡片碎片化** | 每笔账单一张独立浮起卡片，卡片间留 8px 间隙 | 同一日的多笔账单视觉上被拆散，日维度不成立，扫读时视线反复跳跃 |
| **类型编码冗余** | 分类·标签以彩色胶囊承载，金额再以语义色承载，同一行出现两套色彩语义 | 单行色彩噪声过载，语义色（支出红 / 收入绿 / 中性蓝）被稀释，主次倒置 |
| **对齐缺失** | 金额无固定列宽、随文本自然流排；时间以 `ClockIcon` 图标 + 文字呈现 | 金额无法竖向对齐扫读，数十行后丧失「对账」所需的视觉索引 |
| **操作常驻** | 每行常驻编辑 + 删除两个图标按钮（仅靠 hover 显隐） | 行内元素数量居高不下，密集行距被压缩，操作层级扁平 |

### 目标

- **保持简约质感**：不新增装饰性元素、不引入新色系与新圆角语汇，沿用既有令牌体系；
- **大幅升级精致度**：通过结构归位（合组）、对齐纪律（列宽与 tabular）、层级收敛（单一色彩语义）提升完成度，而非通过堆叠视觉特效；
- **边界克制**：仅重构账目流水主页与其必需的底层令牌 / 图标，不触碰顶栏、底部悬浮控件、记账模态窗、统计页与设置页。

### 验收标准

- 同一日的多笔账单在同一连续表面内，日维度一眼可辨；
- 金额列在任意行数下竖向对齐，且语义色为该行唯一色彩承载；
- 行内常态元素压缩至「类型图标 + 描述 + 金额 + 单个更多入口」；
- 320px – 1440px 视口无溢出、无遮挡、无横向滚动；
- 暗黑模式全表面层级可辨（不出现同色背景贴靠）。

## 2. 方案选型记录

规划段产出两版独立原型（禁止单文件堆叠）：

| 方案 | 骨架 | 优势 | 代价 | 结论 |
|------|------|------|------|------|
| **A · 日表层合组** | 每日一张连续表面 + 表头行 + hairline 分隔行；行内左侧类型图标块，右侧金额定宽右对齐 | 层级柔和、扫读快；移动端仅需窄化金额列宽即可，无需重排结构 | 数字列对齐强度略弱于列阵 | **采纳** |
| B · 对账单列阵 | 时间 / 用途 / 分类 / 账户 / 金额 五列严格对齐 + 列头 | 数字对齐最强，桌面端信息密度最高 | 移动端必须降列重排，响应式断点复杂；列头在窄屏退化为纯装饰 | 未采纳 |

**采纳 A 的关键理由**：主页账目的核心作业是「快速定位并核销某一笔」，而非「横向比对多字段」。A 的层级在移动端不坍缩，避免为桌面密度牺牲主作业流的连续性；B 的列头与列阵在 ≤768px 时必须整体降级，实质是同一份 DOM 的两套布局，复杂度收益不匹配（YAGNI）。

## 3. 阶段划分

### Phase 1：设计基座归位

| 项目 | 内容 |
|------|------|
| **输入** | 既有令牌层、图标库、账目流水页当前实现 |
| **输出** | 修正后的中性色令牌（含暗色凹陷面语义）、Mica 类画布底色、四枚语义类型图标、复用的多操作入口图标 |
| **验收标准** | 令牌在明暗两态下均可区分「卡片面 / 凹陷面 / 悬停面」三层次；新增图标为 24×24 视框、`currentColor` 描边、2px 描边宽的纯 SVG，与既有图标库同构 |

> 关键决策：暗色模式下「凹陷面」与「卡片面」当前取同一色值，导致任何依赖该令牌的容器在暗色下失去层次。**在令牌源头修正**，而非在页面局部补色 —— 一次修正同时惠及记账模态窗与设置页的既有容器。

### Phase 2：账目流水页结构重塑

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 令牌与图标；现有分组聚合、日小计、收支隔离计算逻辑（**保持不变**） |
| **输出** | 日表层合组骨架：日容器（圆角由内部表头与末行承担，**不裁剪溢出**）+ 表头（日期 / 星期 / 日小计）+ 行（类型图标 / 描述 + 元信息 / 金额 / 更多入口）+ 行内二级操作浮层 |
| **验收标准** | 收款、转账、还款三类中性记录的账户流向在元信息行完整可读；金额竖向对齐且货币符号与符号前缀规则全局统一；操作入口退至二级后行内常态元素不增加；日小计严格排除还款与转账（沿用现有隔离规则）；末行与单笔分组的二级浮层完整可见可点击 |

> 关键决策：日小计的「排除还款 / 转账」规则与跨年日期补齐逻辑是**业务不变量**，本次仅重排其视觉落位，不触碰计算。表头新增的星期字段须以本地时区构造日期对象派生（`new Date("YYYY-MM-DD")` 在 ECMAScript 中被规范化为 UTC，会致星期错位），复用现有分段解析模式。

### Phase 3：响应式降级与状态收敛

| 项目 | 内容 |
|------|------|
| **输入** | Phase 2 骨架 |
| **输出** | 窄屏金额列宽收窄规则（**元信息不设断点裁剪**）；加载态与空态向新体系对齐；回归验证与文档同步 |
| **验收标准** | 320px 视口下描述文本正常省略、金额不换行、不遮挡相邻行，且元信息各分段完整保留；加载态与空态不残留旧版圆角方块图标容器；前端类型检查与后端全量测试通过 |

## 4. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 排版骨架 | 日表层合组（方案 A） | 移动端不坍缩，主作业流连续 | 对账单列阵（响应式复杂度与收益不匹配） |
| 分组容器形态 | 单一连续表面 + hairline 分隔 | 消除卡片碎片，日维度成立 | 保留独立卡片（视线跳跃，现状问题） |
| 类型编码 | 32px 圆角图标块（支出 ↗ / 收入 ↙ / 转账 ⇄ / 还款 ↺）+ 金额语义色 | 形状编码类型、色彩编码方向，两套通道各司其职；四枚图标须不对称且低笔画密度，保证 16px 下无色可辨 | 彩色文字胶囊（与金额语义色撞车，现状问题） |
| 色彩承载 | 语义色仅由金额承担 | 单行唯一色彩焦点，层级最简 | 分类胶囊着色（冗余编码） |
| 金额对齐 | 定宽 + 右对齐 + 等宽数字 + `${sign}¥${amount}` 统一契约 | 竖向对齐是「对账」作业的视觉索引；符号与货币符号规则统一消除类型间歧义 | 自然流排（现状问题） |
| 容器裁剪 | 日容器不设 `overflow: hidden`，圆角由表头与末行承担 | 行内二级浮层须溢出日容器边界，裁剪会使末行与单笔分组的删除项不可点击 | 容器整体裁剪（与浮层定位物理冲突） |
| 行内操作 | 单个多操作入口 + 二级浮层 | 行内元素压缩，破坏性操作退至二级 | 常驻双图标按钮（行内元素居高不下） |
| 组件复用 | 多操作浮层、语义图标沿用既有库与既有模式 | 不新增交互范式 | 自建新交互（重复建设） |
| 画布材质 | 极淡品牌色顶部径向渐变（Mica 类） | Fluent Layer 0 材质规范，回应「升级质感」诉求且不引入新色系 | 纯平底色（质感提升不足）；重纹理 / 渐变按钮（装饰堆砌，违反简约约束） |
| 令牌修正 | 在令牌层修正暗色凹陷面色值 | 根因处一次修正惠及全部消费者 | 页面局部覆写（补丁式，重复建设） |
| 响应式 | 同一套 DOM，窄屏收窄金额列 + 隐藏次要元信息分段 | 避免双布局与断点分叉 | 独立窄屏布局（同一 DOM 两套结构，YAGNI） |

## 5. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 暗色凹陷面令牌修正后，记账模态窗与设置页既有容器底色随之变化，超出主页重构边界 | 🟡 中 | 该令牌当前在暗色下与卡片面同色、本就无层次；修正属恢复设计意图而非引入新样式。回归时重点目视模态窗与设置页的暗色表现 |
| 表头左右两组内容在 320px 视口碰撞（内容净宽约 248px，收支并存时需约 295px） | 🟡 中 | 表头启用 `flex-wrap`，窄视口下小计整体折至第二行；不叠加按视口切换字号 / 间距的第二套断点 |
| 星期派生若直接 `new Date(dateStr)` 会被规范化为 UTC，UTC 以西时区回退一天 | 🟡 中 | 复用现有分段 `parseInt` + `new Date(year, month-1, day)` 本地构造模式，并在 Task 层列为禁止项 |
| 窄屏隐藏元信息分段后，分类信息在小屏不可见 | 🟢 低 | **已排除该设计**：底部筛选仅按交易大类（全部 / 支出 / 收入 / 转账 / 还款）分流，不存在分类维度，无法在小屏替代分类信息；按视口裁剪有效信息属过度防御，改为全宽度一致 + 单行省略自然截断 |
| 金额字符拼接在类型间不一致 | 🟡 中 | 现有实现支出 / 收入无货币符号而转账 / 还款有；Task 层固定为 `${sign}¥${amount}` 统一契约并引入千分位 |
| 原型为静态示意，与 Task 契约存在脱节（如元信息分段数） | 🟡 中 | 原型按 Task 契约同步修订并在 Task 内显式声明渲染必含字段（`tag_name`），交付段以 Task 为唯一事实来源 |
| 浮层若以命令式 DOM 实现将破坏 React reconciliation | 🟡 中 | Task 层锁定 `openMenuTxId` 声明式状态实现，并要求操作回调触发时同步重置浮层状态 |
| 二级操作浮层在窄屏被视口边缘裁切 | 🟢 低 | 浮层锚定行内操作单元格右对齐，向左展开；沿用既有设置页浮层的关闭与层级约定 |
| 密度提升后长列表滚动性能 | 🟢 低 | 纯 CSS 变换与背景色过渡，无逐帧 JS；不引入虚拟滚动（YAGNI） |
| 语义图标与既有图标库风格漂移 | 🟢 低 | 强制同构约束：24×24 视框、`currentColor`、2px 描边、圆头圆角 |

## 6. Phase 依赖关系

```
Phase 1（设计基座）
   └─→ Phase 2（结构重塑）
          └─→ Phase 3（响应式与状态收敛）
```

严格串行。Phase 2 的排版落位直接消费 Phase 1 产出的令牌与图标，Phase 3 的窄屏规则依赖 Phase 2 的最终行结构。

## 7. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：设计基座 | 中（需读取既有令牌与图标约定） | 低（与 Phase 2 串行） | 主线 | 差分极小且是后续所有视觉决策的参照系，隔离会话的重读成本高于收益 |
| Phase 2：结构重塑 | 强（依赖 Phase 1 令牌 + 既有业务不变量） | 无（严格串行） | 主线 | 涉及业务不变量保护与 DOM 结构重排，主线持上下文直接改最稳 |
| Phase 3：响应式与状态 | 强（依赖 Phase 2 最终行结构） | 低 | 主线 | 与 Phase 2 同文件强耦合，拆分会引入交接损耗 |

> **协同结论**：本阶段全部保留主线。改动集中在单页组件与其直接依赖的令牌 / 图标层，文件间强耦合、串行依赖明确，委托 Subagent 的冷加载重读成本高于其并行收益，不满足委托的正向效益条件。

## 8. 交付边界声明

**本次不改**：顶栏导航、底部筛选胶囊与悬浮记账按钮、记账模态窗、统计页、设置页、后端与接口契约。

上述区域在原型中仅作为上下文出现（用于验证主页与全局框架的材质关系），不落地为代码改动。若评审希望扩大边界，须作为新阶段处理。

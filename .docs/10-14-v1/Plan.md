## 1. 背景与目标

Ledger 业务闭环（收支流水、转账/还款双账户核算、资产负债统计、基础设置）已完整交付，但前端界面停留在「功能可用、层次扁平、令牌松散」的阶段：所有内容均为「描边 + 统一浅阴影」的同质卡片，四段导航、四类交易、四张 KPI 卡在视觉上等权；动效只有两个基础关键帧；删除依赖浏览器原生 `confirm`；暗色模式缺少材质抬升而非仅有阴影。

本次重构**不新增业务功能、不改动后端契约**，只做一件事：把现有界面抬到可与一流商业 App 并列的完成度。

目标（验收的可感知项）：

- 统一的视觉语言：一套令牌驱动全部表面，四层材质（画布 / 内容 / 悬浮 / 模态）肉眼可辨
- 清晰的层级：每个视图有且只有一个视觉焦点，次要信息通过字阶与间距下降，而非通过更多描边
- 细腻的交互反馈：按压、悬停、聚焦、加载、空态、错误态全部有确定表达
- 克制而流畅的动效：统一出场曲线与时长，共享位置过渡（滑块指示器、导航指示器），尊重 `prefers-reduced-motion`
- 完整的状态覆盖：空 / 骨架加载 / 错误 / 成功四态，空态带行动出口

非目标：不改 API、不改数据模型、不引入组件库与 Web 字体、不做响应式之外的多套布局。

## 2. 设计准则（最高准则的具体化）

> 以下不是可勾选的清单，而是判断「某个设计决定是否可以」的依据。凡与之冲突的实现，即使功能正确也应重做。

### 2.1 主设计哲学

沿用项目既有明确约定：**Microsoft Fluent 2**（Project.md 已记录 Fluent-Slate Hybrid 视觉体系）。围绕 Fluent 的五项原则执行：

| 原则 | 本次的具体化表达 |
|------|------------------|
| **Light** | 语义色只服务于「钱的方向」这一种信息；界面其余部分保持中性。禁止为了区分而给不同区块刷不同颜色 |
| **Depth** | Layer 0–3 四层，每层材质不同：渐变画布 → 微投影内容面 → 玻璃悬浮层 → 遮罩 + 深投影模态层 |
| **Motion** | 有目的的短过渡（150–260ms），指示器采用共享位置位移，而非淡入淡出 |
| **Material** | 悬浮层必须毛玻璃 + 1px 高光边；深色模式以「面提亮 + 内高光」代替阴影表达抬升 |
| **Scale** | 4px 间距网格；圆角按容器深度递减刻度取样，不做随机值 |

### 2.2 三条不可违背的纪律

1. **层级来自间距、字重、字号，不来自彩色渐变与描边堆叠。**
   现有界面的核心病症是「每个信息块都是一张描边卡片」，解药是让次要内容**退回画布**（去掉卡片外壳，用发丝线与留白分节），只给焦点内容真正的材质。
2. **一个视图一个主角。**
   流水的主角是「时间流本身」而不是某张汇总卡；统计的主角是「净资产」这一个数字，其余是它的注脚；记账的主角是「金额」这一个输入框。
3. **别怕留白，怕的是解释。**
   所有描述性副标题、教练式提示、元信息自述一律删除；功能入口自解释。保留的只有：校验反馈、加载状态、错误提示、破坏性操作确认。

### 2.3 令牌体系（Phase 1 落盘后全体构件消费）

- **中性**：画布 → 卡片 → 抬升面 → 凹陷面四级灰阶 + 两级发丝线；浅冷调，深色面用提亮而非纯黑
- **品牌**：Fluent `#0078D4` 及其 hover/pressed/浅底/描边五档；深色模式抬升至 `#479EF5`
- **语义**：支出（红）、收入（绿）、转账（蓝）、还款（紫）四色，各自配 `-soft`（淡底）与 `-text`（高强度文本）两档；**淡底只用于图标瓦片与图形，不用于整行背景**
- **半径**：内嵌 6 / 控件 8 / 卡片 12 / 容器 16 / 抽屉 18；嵌套容器逐层减 4
- **深度**：四级阴影令牌 + 深色模式下的 1px 顶部内高光令牌
- **动效**：三条曲线（decelerate 出场、standard 状态、spring 模态）+ 三档时长（120/180/260）
- **排版**：中文优先字栈 + 五档字阶（Hero 数值 / 标题 / 正文 / 次要 / 角标），全站数字 `tabular-nums` 并收紧字距

### 2.4 数据边界纪律（不可虚构）

本次不改动后端，**所有呈现的数值必须能从现有契约派生**：

- 允许：`StatsSummary` 已有字段（`week_expense` / `month_expense` / `last_month_expense` / `month_income` / `month_balance` / `savings_rate` / 分布与趋势 / `asset_summary`）以及它们的四则派生（如资产负债率、花费环比）
- 允许：`Transaction` 列表在本地时区下的分组与小计
- **禁止**：任何需要历史快照或未被返回的计数（净资产月环比、周期笔数等）。原型中出现的同类展示一律以派生指标替换
- 所有比率类派生必须处理分母为 0，输出占位而非 `NaN`

## 3. 阶段划分

### Phase 1：设计令牌与基础构件层

| 项目 | 内容 |
|------|------|
| **输入** | 现有令牌与全部前端构件（参考位置：`web/src/index.css` 与各页面内联样式） |
| **输出** | 完整令牌体系（分层材质、语义色、半径、深度、动效、排版）+ 共享原子构件层（表面、按钮、图标按钮、芯片、分段控件、数值、骨架屏、空态、确认对话框、浮层菜单）+ Layout-0 画布材质 |
| **验收标准** | 深浅两套主题下所有令牌成对存在且有实测对比度；`prefers-reduced-motion` 下所有过渡退化为瞬变；焦点环比全域可见；同一构件在三个页面调用时视觉完全一致 |

### Phase 2：应用外壳与全局反馈层

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 的令牌与原子构件 |
| **输出** | 重制的顶部悬浮导航（滑动指示器 + 玻璃材质）、底部作业条（筛选胶囊 + 主动作按钮）、全局通知（弹簧入场、堆叠、自动计时）、安全解锁浮层、应用级布局与转场；破坏性操作改用应用内确认对话框 |
| **验收标准** | 320px 至 1920px 全区间导航与悬浮作业条不重叠、不溢出；三类通知（成功/错误/信息）语义可辨；主题切换期间无闪白；删除账单不再出现浏览器原生弹窗 |

### Phase 3：账目流水主画布重构

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 构件 + 现有分组逻辑与流水工具函数 |
| **输出** | 月度概览头条（当月支出/收入/结余 + 收支比例导轨，作用域严格限定为当前自然月且不受筛选影响）、日表层组（表头 + 行 + 发丝分隔）、类型瓦片、金额对齐契约、行内二级操作浮层、骨架屏与空态（带建账出口） |
| **验收标准** | 四类交易形态肉眼可辨且共用同一排版契约；跨月数据不混入头条，单一类型筛选下无除零；长文本与超长金额不破版；触摸端操作入口常驻可见；320px 视口无横向滚动；空态提供直达记账的行动出口 |

### Phase 4：统计看板重构

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 构件 + 现有统计数据契约 |
| **输出** | 净资产主视觉（大数值 + 负债占资产比例导轨 + 可派生标记）、无边框发丝分节的本期指标行（含花费环比，分母为 0 时降级）、资产与负债渠道双列明细（含额度导轨）、分类占比环形图与二级标签下钻、六个月收支趋势 SVG 折线图、骨架屏与空态 |
| **验收标准** | 首屏第一视觉落点是净资产；所有图形为自绘 SVG（无第三方图表依赖）；分类下钻状态在同一视口内完成；零数据与满数据版面都不塌陷 |

### Phase 5：记账表单与设置中心重构

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 构件 + 现有业务表单逻辑与校验规则 |
| **输出** | 四段制类型滑块（共享位置指示器）、以金额为唯一主角的输入区、分类渐进披露选择器、双渠道互斥选择、常驻底部操作栏、错误态内联呈现；设置中心的双分区工作台（分类 / 渠道）与细分标签抽屉（窄屏下沉为底部面板） |
| **验收标准** | 移动端键盘弹起时保存按钮永不被裁切；四类记账形态切换零抖动；删除已引用条目给出可读的冲突反馈；抽屉开合具有空间层次但不阻断滚动手感 |

## 4. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 设计哲学 | Microsoft Fluent 2 | 项目已落盘该约定，品牌蓝与中性灰阶构成现有识别 | Apple HIG（需更换品牌色与字栈，收益不抵推翻既有约定的成本） |
| 组件策略 | 自建薄构件层 + 风格化令牌注入 | 保持单二进制零额外依赖；项目仅需十余个原子构件 | 引入 Fluent UI React / shadcn（体量与构建复杂度远超个人部署项目的必要量） |
| 动效实现 | CSS 过渡 + 少量关键帧，过渡走 `transform` / `opacity` | 无需动画库；GPU 合成层，移动端不掉帧 | Framer Motion 等库（新增运行时依赖，与「轻量」约束冲突） |
| 字体 | 系统字栈（Segoe UI / PingFang / 微软雅黑） | 中文字形质量最优、零网络请求、零产物体积 | 引入 Inter / HarmonyOS Sans Web（中文字形仍需回退系统字体，收益不成比例） |
| 图表 | 手写 SVG（折线 + 环形 + 导轨） | 全部图形为纯 SVG，可控的每个像素都参与整体语言 | echarts / recharts（体积大、默认样式与 Fluent 语言冲突，需大量覆写） |
| 状态反馈 | 骨架屏替换旋转指示器；应用内确认对话框替换原生 `confirm` | 原生控件是成品感的最大破坏点；骨架屏保留了布局节奏 | 保留 `window.confirm`（一处系统弹窗即让整屏设计失效） |
| 数据处理层 | 现有业务纯函数与数据契约保持不变 | 本次范围是视觉与交互；业务正确性已被既有测试覆盖 | 一并重构状态管理（超出本次范围，引入不必要的回归风险） |

### 执行主体：全流程主线，不委托 Subagent

原方案将 Phase 3–5 拆给四个并行 Subagent，经审计后**撤销**，理由如下：

1. **视觉一致性是本次交付的生命线。** 被隔离的子会话看不到相邻视图的实际落盘结果，只能依据文字描述各自发挥；在「统一视觉语言、拒绝拼凑感」这一目标下，这种并行等于用工期换掉目标本身。
2. **环境不支持该调度。** 可用子代理类型与并发数上限均不足以支撑四个并发隔离会话；带交付链职责的子代理在同一工作区并行还会引入提交竞争。
3. **地基先行决定了强依赖。** Phase 1 的令牌与构件是所有视图的共同前提，后续视图需要反复对照已落盘的真实样式微调，而非一次性生成。

因此 Phase 1 → 5 全部由主线按序落地，交付段串行执行。代价是总耗时更长，收益是风格收敛与零合并冲突；在明确了「优先美感与整体一致」的前提下，这个取舍成立。

## 5. 风险

| 风险 | 影响 | 应对 |
|------|------|------|
| 原型展示的指标超出后端契约 | 执行时类型报错，或被迫改动后端 | Plan 第 2.4 节锁定数据边界；TASK-012 明确只允许 `StatsSummary` 已有字段及其四则派生；原型中的越界展示已在规划段修正 |
| 流式头条的统计作用域含糊 | 跨月数据混入「当月」、筛选态下除零 | TASK-011 明确头条按当前自然月全类型聚合，不受筛选影响；比率一律除零保护 |
| 串行交付使单阶段改动面变大 | 单次改动文件多，回归定位变慢 | 严格按 Phase 提交节奏推进；每 Phase 结束即跑类型检查与构建，不等到最后 |
| 令牌改名导致大面积文本替换 | 编译期漏改致主题失效 | 交付段以类型检查 + 全量构建为闸门；搜索旧令牌名确认零残留 |
| 图表自绘 SVG 在窄屏溢出 | 统计页移动端破版 | 图形统一 `viewBox` + 百分比宽，禁止固定像素宽；验收含 320px 视口检查 |
| 动效叠加造成低端设备掉帧 | 卡顿感强于精致感 | 动画只作用于 `transform` / `opacity`；列表入场限 4 步进延迟，超出同步进场 |
| 暗色模式仅换色不换材质，仍是「平面堆叠」 | 深色下层级不可辨 | 深色层必须有提亮的面 token 与顶部内高光；禁止深色模式下仅依赖阴影 |
| 骨架屏与真实布局不一致引起跳动 | 加载完成瞬间的版面跳动 | 骨架屏复用真实结构的尺寸类，逐格迭代时高度为 0 也保持占位 |

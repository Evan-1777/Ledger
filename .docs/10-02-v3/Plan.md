## 1. 背景与目标

当前记账系统在生产使用与多端适配中暴露以下三个核心问题：
1. **基础数据重置冲突**：后端 SQLite 初始化时无条件执行默认种子（支付途径、消费类型与细分标签）的 `INSERT OR IGNORE`，导致用户手动删除默认项后，每次重启服务或拉取更新 Docker 镜像都会再次强行注入被删除的项。此外，老数据库升级时缺乏显式事务保护与元数据自动平滑纳管。
2. **移动端顶栏显示拥挤与溢出**：顶栏中央分段导航胶囊的 3 个 `<span>` 页面文案（“账目流水”、“收支统计”、“基础设置”）未配置响应式隐藏，在 360px–414px 手机屏幕下产生挤压与横向溢出。
3. **设置页信息架构过度扁平与功能平铺**：现有设置页以大卡片和网格形式将支付途径、所有分类以及分类下所有标签在一级页面全量平铺，功能入口平权、主次不清、认知负荷高；未引入分层容器（如细分标签专属抽屉）实现渐进式披露（Progressive Disclosure）。

本次演进目标：
- 溯源修复种子注入逻辑，在显式数据库事务中引入 `system_meta` 表并记录初始化状态，确保用户自定义修改/删除在容器重启和镜像升级后持久保留，同时实现老库平滑升级；
- 顶栏中心导航采用项目现有的 `hidden sm:inline` 响应式断点规范：移动端纯 SVG 语义图标彻底解决挤压，桌面端保留文字以维持低认知负荷与易用性；
- 设置页聚焦于真实具备业务支撑的「分类与标签」和「支付途径」两大核心空间，消除无 API 支撑的虚构占位卡片；细分标签管理收敛至专属抽屉（Layer 3 Drawer），保留内联重命名与操作菜单，新增表单延续高效轻量的内联展开交互。

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 种子防重复机制 | `system_meta` 单表状态追踪 + 显式事务 `db.Begin()` | 结构归位：在数据流源头以事务保证建表、检测、种子与元数据写入的原子性；自动平滑检测老库已有数据并补写标记，杜绝每次重启根据单表记录空缺盲目回填 | 环境变量开关（部署复杂、侵入配置）、硬编码跳过（无法支持新用户初始化）、无事务裸写入（异常易致脏库） |
| 顶栏导航形态 | `hidden sm:inline` 响应式断点（移动端纯图标，桌面端图标+文字） | 对齐既有代码规范（Navbar 中登出与 admin 均已采用该断点）；解决移动端挤压的同时，保留桌面端丰富直观的操作语义 | 全端一刀切去字（桌面端大视口下留白过大，初次认知成本增加） |
| 设置页功能范围 | 严格收敛于具备后端真实 API 的「分类与标签」和「支付途径」两大核心区域 | 遵循 YAGNI 与 `production-frontend`：拒绝虚构无后端支撑的静态“系统状态”占位，拒绝虚构不存在底层字段的“快速启闭” | 添加静态假数据面板（属于典型的界面噪声与欺骗性交互） |
| 新增表单交互 | 保留就地展开的轻量内联表单（Inline Form） | 最短有效差分：单文本字段录入无需全屏模态框遮挡已有列表，用户可直接对照已有条目防重输入，且无全局弹窗状态维护负担 | 全屏模态弹窗（Layer 3 Modal 遮挡视野、交互层级过度扩张） |
| 细分标签管理容器 | 基于 SSOT 动态派生的 Layer 3 抽屉容器（Drawer） | 解决 50+ 标签在一级页面全量平铺的严重认知负荷，实现真正的渐进式披露；以 `activeCategoryId` 动态关联 `categories` 状态树，杜绝状态脱节与本地拷贝不同步 | 在一级卡片内就地展开折叠（仍未脱离平铺杂乱与纵深缺失） |

## 4. 风险清单与闭环

| 风险 | 等级 | 缓解与闭环措施 |
|------|------|----------------|
| 老用户升级镜像后，若 `system_meta` 不存在误判为新库导致再次注入已删除项 | 🔴 高 | 检测逻辑严格纳入显式事务：若 `system_meta` 无标记，先探测 `payment_methods`、`categories` 或 `transactions` 是否已有数据；若已有数据判定为已有老库，直接补写 `seed_initialized = 'true'`，绝不重复插入种子；并在 `db_test.go` 中建立专门的老库升级单元测试用例 |
| 抽屉内标签操作与父级 `App.tsx` 状态脱节 | 🟡 中 | 抽屉仅维护 `activeCategoryId`，所有标签数据由 `categories.find(c => c.id === activeCategoryId)?.tags` 实时派生；修改/添加/删除统一调用 `App.tsx` 传入的 async handler，操作成功后驱动 `fetchConfigData()` 刷新并维持抽屉内当前视图 |
| 抽屉交互退化导致防重校验与 409 拦截丢失 | 🟡 中 | 严禁使用原生 `window.prompt` / `window.confirm`；抽屉内标签编辑复用同构内联输入框与同级防重校验；删除调用 API 捕获 409 错误并通过 Toast 输出清晰中文拦截提示 |

# Plan：Android 订阅页功能支持

**状态**：DONE（2026-10-31 交付完成）
**日期**：2026-10-31
**版本**：v1.1（2026-10-31 评审修订）
**依据**：用户 Main-Hybrid 需求、.docs/SCOPE.md、.docs/Project.md、Web 订阅页与后端订阅接口、Flutter 客户端既有架构与测试基线
**设计基线**：Material 3（Android 客户端既定视觉体系），复用现有卡片、确认框、弹出菜单、底部表单与空/错/骨架态构件

## 1. 背景与目标

### 现状

后端已提供订阅分组与订阅的八个鉴权端点，Web 端已交付第五个一级「订阅」页；Android 客户端仍是四段导航（流水 / 统计 / 资产 / 设置），没有任何订阅入口。订阅数据与流水、统计、资产、设置共用同一套 HTTP API，但客户端尚未建立对应模型、状态与页面。

### 本轮目标

在 Android 客户端补齐与 Web 对齐的订阅固定开支能力：

- **五段导航**：新增「订阅」一级入口，顺序为流水 / 统计 / 订阅 / 资产 / 设置，现有四页行为不变。
- **月度总览**：只统计使用中的订阅，展示每月合计、年度预估、未来 7 天待扣金额与项数；暂停项不计入。
- **分组展示**：按用户分组分区展示使用中项数、有效月合计与分组标识色；支持新建、重命名、上移、下移、删除分组。
- **订阅管理**：新增、编辑、删除、暂停续费、恢复续费；字段为服务名、分组、每月金额、扣款日、状态。
- **可读状态**：全部 / 使用中 / 已暂停筛选；加载、错误、空、成功四态；删除与删组均有确认；操作结果通过既有 SnackBar 反馈。
- **数据一致**：订阅数据进入统一控制器，登录后随全量加载拉取，变更后重新拉取；不做乐观更新；401 沿用既有会话失效链路。
- **尺寸与可访问性**：320dp + 2 倍字体下无溢出、无不可达操作；菜单、表单与确认框可正常打开和关闭。

### 明确的范围外

- 不改后端、不改 Web、不改数据库结构；Android 只消费既有八个端点。
- 不做年付 / 季付 / 周付、自动记账、续费通知、推送、日历、多币种、服务商 Logo、搜索或拖拽排序。
- 不扩展冷启动快照：订阅是独立页面，在线拉取失败时显示错误态与重试；本轮不把订阅写入本地缓存。
- 不新增第三方依赖，不调整 Flutter SDK 或依赖版本，不提升应用版本号（发布动作由后续发布阶段决定）。
- 不重构流水、统计、资产、设置页面的既有布局与业务口径。

## 2. 阶段划分

### Phase 1：客户端契约与状态层

| 项目 | 内容 |
|------|------|
| **输入** | 后端八个订阅端点的字段与错误语义、现有模型解析约定、统一控制器与请求代际模式 |
| **输出** | 订阅状态、分组、订阅与提交输入模型；八个 API 客户端方法；控制器中的分组/订阅列表、加载态、错误态、代际与 CRUD 方法；重复分组名的中文错误映射 |
| **验收标准** | 模型可正确解析空 group_id、金额分/元、状态枚举；全量加载能拉取订阅；401 触发会话失效并清空业务数据；既有控制器用例与全量测试不回归 |

### Phase 2：订阅派生纯函数

| 项目 | 内容 |
|------|------|
| **输入** | 本地日期语义、扣款日 1–31、暂停状态与分组排序规则 |
| **输出** | 下次续费日推导、整日差、月度/年度/未来 7 天汇总、状态筛选、分组分区与排序；对应纯函数测试 |
| **验收标准** | 短月夹取、跨年、当天扣款、7 天边界、暂停排除、空分组、未分组末尾均有可执行用例；金额汇总只使用整数分 |

### Phase 3：订阅与分组表单

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 的提交模型与控制器方法、现有底部表单与确认框交互约定 |
| **输出** | 订阅新增/编辑底部表单（名称、分组、月金额、扣款日）；分组新建/重命名对话框；字段校验、提交中禁用、失败保留输入 |
| **验收标准** | 空名称、金额越界、扣款日越界、重复分组名（大小写不敏感）无法提交；320dp 下表单可滚动、键盘不遮挡保存；提交期间禁止下滑/遮罩/返回关闭，成功后关闭并刷新，失败保留表单与输入 |

### Phase 4：订阅页、五段导航与管理动作

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1–3 的模型、派生函数、表单与既有页面视觉构件 |
| **输出** | 第五个一级订阅页（Hero、筛选、分组分区、行、空/错/骨架/筛选空态）；五段导航与索引归位；行/分组菜单；暂停恢复、删除订阅、删除分组、分组调序与「在此分组添加」 |
| **验收标准** | 使用中与暂停互斥计入；分组小计等于组内使用中金额之和；删组后订阅进入未分组且仍计入 Hero；所有管理动作有成功/失败反馈；首次加载失败只显示页面错误态、刷新失败才走 Shell 提示；320dp + 2 倍字体无溢出与不可达操作；既有四页导航与设置分区直达不回归 |

### Phase 5：测试、文档、归档与提交

|------|------|

| **输出** | 页面 Widget 测试与新增 API/控制器用例；格式、静态检查、全量测试、Web 编译门禁；Project.md 同步；Plan/Tasks 归档；白名单提交 |

## 3. 架构与关键决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 状态归属 | 订阅分组与订阅进入现有统一账本控制器 | 与流水、统计、配置保持同一 SSOT；401、清空、错误提示与加载代际可复用；页面无需额外 Provider 装配 | 页面内自持状态（登录切换与 401 需重复处理，测试注入更繁琐）；新增独立 Controller（多一套生命周期与错误通道，本轮无跨页共享需求） |
| 加载时机 | 登录后的全量加载包含订阅，页面下拉刷新单独拉订阅 | 与「登录后一次加载全部业务域」的既有约定一致；第五个 Tab 随 IndexedStack 常驻，不存在按需挂载的懒加载收益 | 首次切到订阅 Tab 再加载（需额外标记与分支，且 IndexedStack 已构建页面，收益有限）；页面 initState 加载（生命周期分散，登录切换难联动） |
| 导航顺序 | 流水 / 统计 / 订阅 / 资产 / 设置 | 与 Web 五段导航一致，订阅属于高频固定开支视图，放在资产之前 | 追加到末尾（与 Web 认知顺序不一致）；收纳进「更多」（一级入口被降级） |
| 导航索引 | 设置与订阅索引收敛为命名常量 | 原代码用裸数字 3 表示设置；插入第五项后裸索引必然错位，常量让入口单一可读 | 全局替换为枚举（改动面大于收益，本轮只有两个固定索引） |
| 页面视觉 | 沿用现有 Material 3 卡片、金额层级、语义色与紧凑顶栏 | 与 AssetsScreen / StatsScreen 同一视觉语言；不复制 Web 的 Fluent 玻璃材质 | 照搬 Web 令牌（Flutter 端无对应材质体系，破坏一致性） |
| 筛选控件 | 可换行 ChoiceChip 组（全部 / 使用中 / 已暂停） | 后两个标签为三字，三段等宽在 320dp + 2x 下所需宽度超过 288dp；ChoiceChip 可换行且与统计筛选面板同一语义，不裁剪文案 | 等宽 SegmentedButton（2x 下溢出）；缩短为「在用 / 暂停」（文案不自然）；横向滚动（隐藏选项） |
| 分组选择 | 表单内下拉选择，未分组用 0 哨兵并转换为 null | 避免空值菜单项的显示歧义；与后端「0 视为未分组」语义一致 | 分组字符串（改名需批量更新）；底部选择面板（多一层容器，字段少时过重） |
| 分组调序 | 按目标顺序重写 1..N，仅提交有变化的项 | 顺序稳定，不依赖原 sort_order 是否连续；与 Web 行为一致 | 互换两项 sort_order（历史数据有重复值时可能无视觉变化，需要额外兜底） |
| 删除分组 | 只调用删除端点，依赖外键 ON DELETE SET NULL | 后端已保证组内订阅转为未分组；客户端重复迁移会形成双重保障与额外失败面 | 客户端先批量改组再删组（多请求、半失败状态复杂） |
| 首次失败与刷新失败 | 首次加载失败只显示页面错误态与重试，不进入 Shell SnackBar；已有订阅数据时的刷新失败保留数据并由 Shell 提示 | 避免同一次失败同时出现页面错误面板与全局提示；刷新失败仍有可感知反馈与下拉重试 | 两者都走 Shell（首次失败双提示）；两者都走页面（刷新失败缺少全局反馈，且与既有四页不一致） |
| 冷启动缓存 | 不扩展 | 订阅不是默认落地页，本轮不引入缓存信封版本与地址隔离的新测试面 | 扩展现有三域快照（改动跨存储、控制器与测试，超出单页功能范围） |
| 图表配色 | 分组与未分组统一取 chart[index % chart.length] | 现有图表色阶只有 5 色，未分组下标等于分组数，直接取色会在 5 组 + 未分组时越界 | 为分组单独存颜色（多字段与取色 UI）；只在未分组特殊兜底（与分组取色规则不一致） |
| 版本与依赖 | 不改版本号，不新增依赖 | 本轮只补客户端功能；APK 发布由版本与 tag 流程单独决定 | 顺手升级（违反项目锁定版本约定） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 第五个 NavigationBar 目标在 320dp + 2 倍字体下溢出或标签截断 | 高 | 沿用两字标签；新增 320dp + 2x Shell 用例；必要时只收紧导航标签行为，不改四页内容 |
| 插入订阅后设置索引仍按 3 处理，导致点「设置」进入资产或分区错位 | 高 | 设置/订阅索引改为命名常量，更新分区重置与渠道直达；Shell 用例覆盖五段切换与返回键 |
| 全量加载新增订阅请求，既有测试假服务按路径返回列表，导致 POST/PUT 解析单对象失败 | 高 | 测试假服务按「方法 + 路径」返回列表/单对象/成功体；defaultApi 与控制器标准处理器共用一个订阅响应 helper；跑全量回归确认 SnackBar 仍为单条 |
| 扣款日 29–31 在短月不存在，下次续费日漂移 | 中 | 纯函数夹取当月最后一天；2 月、4 月、12 月跨年、当天扣款各有用例 |
| 未来 7 天边界把第 7 天或今天算错 | 中 | 固定 0–6 的整日差；7 天边界与当天用例；金额只累加使用中 |
| 分组调序中途失败，客户端顺序与服务端不一致 | 中 | 每次调序结束都重新拉取；失败路径由统一异常上抛并提示；不做乐观排序 |
| 底部表单在 320dp、键盘弹出或 2x 字体下按钮被遮挡 | 中 | 键盘 inset 内边距 + 可滚动表单 + 固定底部安全区；320dp 用例覆盖打开与滚动 |
| 筛选胶囊、Hero 次列、组头与行内金额在 320dp + 2x 下换行或挤压 | 中 | 筛选改可换行 FilterChip；Hero 次列用两列 Expanded + 值 FittedBox、标签允许换行；组头名称/小计一行、项数单独一行；行内金额 Flexible + FittedBox；320dp 用例断言关键文本矩形在视口内且无异常 |
| 筛选后空分组与未分组分区的管理入口丢失 | 中 | 「全部」保留空分组与添加入口；仅 active/paused 过滤隐藏无匹配分区，与 Web 一致 |
| 订阅合计混入暂停项或使用浮点累加 | 中 | 汇总只读 amount_cents 且仅 active；单元用例覆盖暂停排除与分组小计 |
| 5 个分组加未分组时图表取色越界 | 低 | 分组与未分组统一用 index % chart.length；补 5 组 + 未分组用例 |
| 首次订阅失败同时出现页面错误态与 Shell SnackBar | 中 | 订阅错误仅在已有订阅数据时进入 Shell 错误链；补部分请求失败用例 |
| 变更后刷新失败导致用户以为数据已保存但页面仍旧 | 低 | 变更成功才关闭表单并提示；刷新失败保留数据 + Shell SnackBar；下拉刷新可重试 |
| 归档移动后仍按根目录路径 add，命令失败；直接 commit 会把既有暂存文件带入 HEAD | 高 | 归档后只 add 归档目录；提交用 git commit -m 消息 --only -- 白名单路径；不执行 git reset / git add -A；提交前后核对暂存清单与 HEAD 文件清单 |

## 5. Phase 依赖关系

Phase 1 → Phase 2
Phase 1 → Phase 3 → Phase 4 → Phase 5

Phase 1 的模型与控制器决定 Phase 3 表单和 Phase 4 页面的数据来源；Phase 2 的派生函数被 Phase 4 直接消费；Phase 5 依赖完整实现与门禁结果。Phase 2 可在 Phase 1 模型定型后与 Phase 3 并行阅读，但写入保持串行。

## 6. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|------------|----------|----------|----------|
| Phase 1：契约与状态 | 强（统一控制器、代际、401 与既有测试假服务） | 无 | 主线 | 改动集中在同一条数据链路，拆分会增加契约对齐成本 |
| Phase 2：派生纯函数 | 中（字段与业务规则已定型） | 低 | 主线 | 用例与实现边界需要同步推演，测试量不足以抵消交接成本 |
| Phase 3：表单 | 强（既有底部表单、输入格式化与错误提示惯例） | 无 | 主线 | 表单细节依赖页面状态与控制器方法，隔离会话难以保持一致性 |
| Phase 4：页面与导航 | 强（视觉节奏、菜单、空态与窄屏约束互相牵制） | 低 | 主线 | 单页面的布局与交互需在同一上下文中收敛 |
| Phase 5：测试与文档 | 中（需汇总全部决策与门禁结果） | 低 | 主线 | 文档必须逐条对齐实际实现，主线书写更可靠 |

> **协同结论**：本轮是单页面、强串行、上下文高度耦合的客户端交付，不派发 Subagent，全部由主线执行。

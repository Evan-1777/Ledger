## 1. 背景与目标

Ledger 当前已完成 Go + React + Vite + Tailwind + SQLite 的基础脚手架搭建与单二进制嵌入链路。本项目定位为个人轻量记账工具，运行于个人环境或 VPS，无多租户需求。

本次规划旨在落地核心记账业务闭环及配套前端：
- 采用极简的管理员单一密码鉴权模型，无需复杂的账号管理系统；
- 支持单笔记账录入，具备智能金额正负判定（默认支出为负、输入“+”为正），并实现类型与细分标签的联动机制；
- 提供完整的支付途径、类型和二级细分标签管理功能（设置页）；
- 提供本周花费、当月花费、上月花费的清晰数据统计指标（统计页）；
- 前端全面遵循 Microsoft Fluent 2 设计规范与 Z 轴四层物理层级，杜绝界面噪声，打造精致耐看的数据操作体验。

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 鉴权模型 | 单一管理员密码 + HMAC 会话凭证 | 个人私有部署工具，无需注册/角色分配，符合 YAGNI 与零复杂度原则 | 多用户 RBAC / OAuth2（严重过度设计，增加数据表与交互负担） |
| 账单金额存储 | 带符号整数分（`amount_cents INTEGER`，负为支出、正为收入） | 彻底消除 IEEE 754 浮点累加漂移，SQLite 原生保证统计精确到分；API 层按元展示 | 浮点数 REAL 存储（存在二进制精度漂移，无法满足财务数据准确性要求） |
| 标签级联机制 | 细分标签归属于具体类型（外键关联） | 满足需求中“类型细分标签、选择不同类型标签不同”的强业务约束 | 扁平标签池（无法实现类型维度的精细化收敛与归类） |
| 时间存储口径 | RFC3339 UTC 字符串存储，查询前换算本地时区边界 | 数据库存储标准无歧义；服务层以本地日历时间判定自然周与自然月起止，转为 UTC 区间精确查询 | 存储无时区本地时间（跨时区部署或切换环境时历史统计全部错位） |
| 前端视觉体系 | Microsoft Fluent 2 | 契合用户明确要求，提供专业高质感的光感、微质感与深度分层体验 | Apple HIG / 纯扁平 Tailwind 默认（未能满足用户指定的 Fluent 风格） |
| 组件构建策略 | 原生语义组件 + 注入 Fluent 2 材质令牌 | 极简自洽、依赖轻量，无缝契合现存 Tailwind 配置，杜绝第三方重型库膨胀 | 引入体积庞大的完整 Fluent UI React 库（在极简个人应用中造成数百 KB 的额外打包负荷） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 自然周与自然月跨月跨年统计的时间区间计算偏差 | 🟡 中 | 统一采用 RFC3339 UTC 存储；服务层以本地时区获取自然周/月零点并转为 UTC 边界执行范围查询，单元测试覆盖跨月跨年边界 |
| 删除类型时关联细分标签或历史账单产生孤儿数据或静默误删 | 🟡 中 | 数据库外键开启 RESTRICT 约束；应用层统一守卫：被 transactions 引用的分类、标签或支付途径删除时均返回 409 Conflict 明确拦截 |
| VPS 公网部署弱密码被暴力枚举破解 | 🟡 中 | 默认密码未更改时控制台打印安全警示；登录校验失败强制引入 500ms 时延，以极小代价遏制暴力爆破 |
| 长期无操作导致管理员鉴权凭证失效 | 🟢 低 | 前端请求拦截器统一捕获 401 并保留当前表单输入内容，重新输入密码后自动重试 |

## 5. Phase 依赖关系

```
Phase 1 ──→ Phase 2 ──→ Phase 4 ──→ Phase 5
                 │           ▲
                 ▼           │
              Phase 3 ───────┘
```

- Phase 1（数据库与鉴权）为后端基石；
- Phase 2（后端业务 API）与 Phase 3（前端 Fluent 底座）可并行或顺次推进；
- Phase 4 依赖 Phase 2 接口与 Phase 3 界面外壳；
- Phase 5 汇总验收并完成构建交付。

## 6. Subagent 协同规划

对照三维效益模型（任务复杂度、上下文关联度、经济与时间效益）评估本阶段委托需求：

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：数据持久层与鉴权 | 强（涉及全局 schema 与安全契约） | 低（全局基础） | 主线 | 避免隔离会话造成契约错位 |
| Phase 2：业务 API 与统计核心 | 强（依赖 Phase 1 数据层） | 低（核心连续链路） | 主线 | 统一接口规范与数据转换 |
| Phase 3：前端 Fluent 底座 | 中（依赖原型设计与样式规范） | 中（可自包含完成样式封装） | 主线 | 确保 Fluent 视觉与层级准确落地 |
| Phase 4：三大主页面业务实现 | 强（联动前后端业务上下文） | 中（多页面可按模块渐进完成） | 主线 | 交互细节多，集中处理上下文更平滑 |
| Phase 5：测试与构建归档 | 低（只读验证与自动化命令执行） | 高（端到端自包含） | Subagent: executor | 边界清晰且耗时较长，由 Executor 自动化推进可大幅缩短端到端交付用时 |

> **协同结论**：Phase 1 至 Phase 4 涉及核心模型演进、前后端接口与界面强上下文联动，由主线保持最高专注度与准确度贯穿实现；Phase 5 构建验证、打包与文档归档委托 `Subagent: executor` 完成。

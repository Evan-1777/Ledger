## 1. 背景与目标

### 现状与根因

| 编号 | 现状 | 根因 |
|------|------|------|
| A | Android 端流水筛选下拉的选项高亮是直角，与菜单圆角不统一，首末项高亮越过圆角形成尖角 | 弹出菜单默认不裁剪内容，菜单主题只能配置外框形状，子项点击态按矩形绘制并溢出圆角 |
| B | 统计只有支出构成、支出渠道分布与支出指标卡；收入仅出现在结余头条与 6 个月趋势 | 统计接口的分类/渠道分布与周、上月指标只按支出口径聚合；客户端统计页也只有一套支出视角 |
| C | 任何分类的收支都会进入统计，无法排除「资金转入转出」这类非真实收支 | 分类维度没有统计口径标记，所有收支聚合都缺少分类级过滤 |
| D | 分类行看不出某个分类是否被计入统计；流水页的日小计仍按全部分类求和 | 统计口径状态不可见，且日小计没有接入同一口径，排除后同页会出现「本月支出 0 / 当日支出 100」的自相矛盾 |

### 本轮目标

- **下拉视觉统一**：所有弹出菜单按自身圆角裁剪内容，选项高亮不再越过圆角。
- **收入统计补全**：后端补充周收入、上月收入、收入分类构成、收入渠道分布；Android 统计页提供「支出 / 收入」统计视角，指标卡、构成图（含环形图中心与语义文案）、渠道分布随视角切换。
- **统计排除分类**：分类支持「不计入收支统计」开关；后端所有收支聚合（周/月/上月金额、分类与标签构成、渠道分布、6 个月趋势、结余与储蓄率）统一排除这些分类；客户端流水日小计使用同一口径；资产负债核算不受影响。
- **可验证**：后端集成测试覆盖收入字段、分布排序与百分比、排除过滤的精确数值；客户端 Widget 测试覆盖收入视角、排除开关、日小计口径与菜单裁剪配置。

### 明确的范围外

- 不做标签级或单笔级排除（需求为分类级）。
- 不改资产负债口径：被排除分类的资金流动仍真实改变账户余额。
- 不改 Web 端界面：统计接口只新增字段，字段名与结构不变；既有字段的**数值口径**会随排除分类变化，Web 自动继承，但不提供收入视角与排除开关（Web 为开发/自检面）。
- 不引入图表或下拉菜单第三方依赖。

## 2. 阶段划分

### Phase 1：分类统计排除标记（存储与设置接口）

| 项目 | 内容 |
|------|------|
| **输入** | 现有分类表结构、老库热迁移机制、分类 CRUD 接口 |
| **输出** | 分类新增统计排除布尔列；全新建库与老库升级均可获得该列；分类接口可读写该字段，未传时保留原值 |
| **验收标准** | 全新建库与老库升级后列存在且默认未排除；创建/更新/列表往返一致；更新时不传该字段不改变已有值 |

### Phase 2：统计口径（收入补全 + 排除过滤）

| 项目 | 内容 |
|------|------|
| **输入** | Phase 1 的分类标记、现有统计聚合与错误契约 |
| **输出** | 收入汇总与收入构成/渠道分布字段；支出与收入共用同一套聚合逻辑，按类型决定排序与百分比分母；所有收支聚合按分类标记过滤 |
| **验收标准** | 收入分布按金额降序且百分比以同口径总额为分母；把某分类置为排除后，收支汇总、构成、渠道、趋势、结余与储蓄率同步下降；资产负债字段不变 |

### Phase 3：Android 弹出菜单裁剪

| 项目 | 内容 |
|------|------|
| **输入** | 现有菜单圆角主题与全部菜单入口 |
| **输出** | 每个菜单入口统一启用内容裁剪，内容与高亮都收敛在圆角内 |
| **验收标准** | 菜单内容不再溢出圆角；Widget 断言覆盖全部菜单入口的裁剪配置；既有菜单交互测试不回归 |

### Phase 4：Android 收入视角、日小计口径与分类排除开关

| 项目 | 内容 |

| **输出** | 统计页「支出 / 收入」视角切换（置于结余头条与指标卡之间，全宽分段控件；不重置「构成 / 趋势」选择，趋势始终双线）；环形图中心与语义文案随视角；流水日小计按同一分类口径过滤；分类操作菜单新增统计口径切换，行内展示当前口径 |
| **验收标准** | 切换视角后标题、指标卡、构成、渠道与中心文案全部来自对应字段；排除分类后日小计与本月头条一致；开关写入后统计刷新；320dp 与 2 倍字体下同时切换视角与图表模式无溢出；默认支出视角与现状一致 |

## 3. 关键决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 排除粒度 | 分类级布尔标记 | 用户诉求是「某些分类不是收支」；分类是流水必填维度，标记在分类上即可覆盖其全部流水 | 标签级/单笔级排除（组合爆炸、录入成本高、需求未提） |
| 字段语义 | 独立于收支类型的「不纳入统计」标记 | 与需求语义一一对应，不与业务类型混淆 | 复用转账类型或隐藏标记（把统计口径与业务分类绑死） |
| 过滤位置 | 服务端统一过滤，客户端只对日小计复用同一标记 | 统计、结余、储蓄率、趋势共用同一口径；日小计不依赖服务端聚合，只能用分类标记复算 | 客户端按分类过滤全部统计（多端重复、易与头条口径不一致） |
| 分布排序 | 按金额绝对值降序 | 支出为负数、收入为正数，沿用支出用的升序会让收入从最小排到最大；绝对值降序对两种类型都成立 | 按类型切换升降序（两套分支，易漏改） |
| 百分比分母 | 使用同类型过滤后的当月总额 | 收入与支出的分母不同；用错会让占比合计偏离 100% | 固定用支出总额（收入占比全错） |
| 资产负债口径 | 不受排除影响 | 资金确实转入转出，账户余额必须真实；排除只针对收支统计 | 同步排除（余额与流水对不上，破坏净资产守恒） |
| 收入分布 | 与支出分布共用聚合，仅按类型参数收敛 | 结构、百分比规则一致，只有类型、排序与分母不同；避免两套重复逻辑 | 复制一套收入查询（后续改口径要改两处）；抽象成通用查询框架（本轮无第二个维度，过度设计） |
| 客户端呈现 | 统计页「支出 / 收入」视角切换，位于头条与指标卡之间，全宽分段控件 | 复用指标卡、构成图、渠道分布，不额外堆叠整页；全宽控件在 2 倍字体下不溢出 | 新增独立收入分区（页面翻倍长，构成图代码重复）；放在图表卡头部（与「构成/趋势」挤在一行，2x 下溢出） |
| 视角与图表模式关系 | 切换视角不重置「构成 / 趋势」；趋势始终双线收支 | 不打断用户当前的图表选择；趋势本身就是收支对比，与视角无关 | 切视角强制回「构成」（用户选择被重置） |
| 默认视角 | 支出 | 保持现有用户心智与既有断言；收入为显式切换 | 默认收入（与现状断裂） |
| 日小计 | 随统计口径过滤，副标题仍展示全部流水 | 同页「本月支出」与「当日支出」必须一致；流水条目本身仍完整展示 | 保留全量小计（同页数字自相矛盾）；连流水条目一起隐藏（丢失真实资金记录） |
| 环形图文案 | 中心文案与语义标签参数化 | 固定「本月支出」在收入视角会语义错误，无障碍标签同样错误 | 保留硬编码（可见错误） |
| 菜单裁剪 | 逐个入口启用裁剪 | 菜单主题没有可配置的裁剪入口，框架层无全局开关 | 自建菜单封装（为少量调用点引入泛型包装，收益不足） |
| 排除开关入口 | 分类行溢出菜单 + 行内状态文案 | 与重命名/调序/删除同层，不新增入口层级；行内文案提供可见反馈 | 分类编辑对话框加开关（打断命名流程，且需扩展对话框状态） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 排除分类后历史统计与用户预期不一致（数据「消失」） | 中 | 分类行显示「不计入统计」；开关即时刷新统计；文案明确限定为收支统计 |
| 过滤条件漏加导致口径不一致（例如趋势仍计入） | 高 | 收支聚合收敛到共享逻辑；集成测试同时断言汇总、分布与趋势 |
| 收入分布排序反向或百分比分母错配，界面数字错误但测试仍绿 | 高 | 排序统一用绝对值降序；分母取同类型过滤后总额；测试断言首项名称、顺序与百分比数值 |
| 日小计未接入口径，同页出现矛盾数字 | 中 | 日小计接收排除分类集合；补当日全部被排除的用例 |
| 老库升级缺列导致运行期查询报错 | 高 | 沿用既有列探针热迁移；全新建库与迁移测试都断言列存在与默认值 |
| 统计接口新增字段导致客户端测试夹具编译失败或旧缓存被判损坏 | 中 | 新字段按严格模型补 required 并同步夹具；JSON 解析对缺省字段容错 |
| 统计页视角切换在小屏 + 2 倍字体下溢出 | 中 | 视角切换采用全宽分段控件（与设置页同构）；保留 320dp + 2x 双切换用例 |
| 菜单裁剪裁掉阴影或改变弹出位置 | 低 | 裁剪只作用于内容层，阴影由外层绘制；Web 自检截图核对 |
| 本机 Android 工具链缺失，门禁被误记为通过 | 中 | 门禁写明工具链前置与完整命令，逐条记录退出码；真机视觉效果由 CI 产物验收 |

## 6. Subagent 协同规划

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|-----------|---------|----------|----------|
| Phase 1：分类标记与接口 | 强（表结构、迁移约定） | 无 | 主线 | 差分小且与 Phase 2 同域，拆分会增加合并成本 |

| Phase 3：菜单裁剪 | 弱（少量单行改动） | 低 | 主线 | 改动过小，委托开销高于收益 |
| Phase 4：客户端统计、流水与设置 | 强（页面结构、文案与既有测试契约） | 无 | 主线 | 涉及统计页重构与断言同步，隔离会话需重建大量上下文 |
| Phase 5：门禁与文档 | 中 | 低 | 主线 | 需基于本轮全部决策书写文档，委托反而增加交接成本 |

> **协同结论**：本轮改动集中在后端统计与客户端统计页，上下文强相关且链路串行，全部由主线执行；不派发 Subagent。

## 1. 背景与目标

### 现状

Web 端当前是四段导航的单页应用（流水 / 统计 / 资产 / 设置），导航由 React 状态切换，没有路由。设置页负责分类、标签、资产/负债渠道；统计页只聚合真实账单，缺少“每月固定会发生的服务开支”这一层定义。订阅支出如果直接记账，既不能提前知道每月总额，也无法在涨价、暂停、换组时保持清晰。

### 本轮目标

新增第五个一级页面「订阅」，作为固定服务开支的单一维护入口：

- **月度总览**：只统计使用中的订阅，展示每月合计、按 12 个月估算的年度支出、未来 7 天待扣金额与项数；暂停项不计入。
- **分组展示**：按用户定义的分组分区展示；每个分组显示使用中项数、有效月合计和分组标识色；分组可新建、重命名、上下移动、删除。
- **订阅管理**：新增、编辑、删除、暂停续费、恢复续费；每条包含服务名、分组、每月金额、扣款日、状态。扣款日只存 1–31 的日号，下次续费日由客户端按本地日期推导，短月自动落到月末。
- **可读状态**：全部 / 使用中 / 已暂停筛选；空、加载、错误、成功四态；删除与分组移除均有确认；操作结果通过现有 Toast 反馈。
- **持久化**：数据写入 SQLite 并通过鉴权 API 读写，不使用 localStorage 镜像；刷新页面或多端访问保持一致。
- **导航适配**：第五个 Tab 进入页面；五个一级入口在 320/360/400/420px 宽度下不溢出、不遮挡。

### 明确的范围外

- 不做年付 / 季付 / 周付等计费周期，不计算“年付折算月”。本轮按用户描述只管理按月续费的服务。
- 不自动生成真实账单，不把订阅金额写入流水或统计；订阅是“预期固定开支”，不是已发生交易。
- 不做续费通知、系统推送、邮件提醒或日历集成。
- 不做服务商 Logo 抓取、多币种、汇率换算、导出、搜索、分组筛选、手动拖拽排序。
- 不改 Flutter Android 客户端；本轮只交付 Web，API 与数据模型保持语言无关，Android 订阅页另立阶段承接同一接口；不动既有统计、流水、资产、设置业务口径。
- 不引入前端测试框架、图表库、日期库或新的运行时依赖。

## 3. 架构与关键决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 数据归属 | SQLite + 鉴权 HTTP API | 与现有单一事实来源一致，刷新、换端、备份都可靠；个人 VPS 场景不需要额外同步层 | localStorage（换浏览器即丢失，与既有架构冲突）；仅内存（刷新丢失） |
| 分组模型 | 独立分组表，订阅持有可空 group_id | 分组需要排序、重命名、删除与空组管理；可空外键天然承载「未分组」，组名 COLLATE NOCASE 唯一，删除分组不会删除订阅 | 订阅表存分组字符串（改名要批量更新、排序无依据）；固定枚举（用户不能自定义类型） |
| 金额存储 | 整数分；API 同时返回 amount_cents 与 amount | 汇总和年度估算用整数分避免浮点误差；展示字段与现有 API 风格一致 | 只用浮点（多次求和会出现精度漂移）；只用分（前端各处重复除 100） |
| 计费周期 | 仅按月，存扣款日 1–31 | 用户明确描述「每月续费」；不引入周期枚举、折算规则和年付边界 | 支持月/季/年（需要折算、下期日期与总额口径，超出本轮） |
| 下次续费 | 客户端由日号 + 本地今天推导，不落库 | 避免服务端时区与客户端不一致；改扣款日即自动得到新日期；短月按月末收敛 | 存绝对日期（每次续费后要写回，容易过期）；服务端计算（时区边界与客户端显示不一致） |
| 状态 | active / paused 二态；暂停项保留定义但不计入合计和未来 7 天 | 用户会临时停掉服务但不想删除记录；恢复后无需重填 | 删除代替暂停（丢失历史与配置）；增加归档态（本轮无历史账单，无意义） |
| 删除分组 | 组内订阅转为未分组，不级联删除 | 符合“管理分组”而非“删除数据”的语义，避免误删固定开支 | 有订阅时拒绝删除（用户要先逐条迁移，成本高）；级联删除（危险） |
| 页面数据 | 订阅页自行加载与刷新，不把订阅状态提升到 App | 订阅与流水/统计/设置没有共享派生关系；页面卸载即释放，避免 App 继续膨胀 | 全部塞进 App（跨页无收益，增加耦合）；全局 store（本轮无跨页订阅需求） |
| 登录后刷新 | 页面接收鉴权状态，登录成功后重新加载 | 未登录时页面可能已挂载；仅靠挂载时请求会在登录后停留在错误态 | App 强制重挂载（隐式、脆弱）；忽略（错误态不恢复） |
| 导航文案 | 五项统一两字：流水 / 统计 / 订阅 / 资产 / 设置 | 五个四字标签在 640px 附近会挤压；两字标签保留语义并让滑动指示器等宽 | 保留四字（需要额外的响应式断点或横向滚动）；收纳进“更多”（一级入口被降级） |
| 空分组 | 在「全部」视图保留分区，显示 0 项和添加入口 | 空组仍可重命名、删除、调序，避免“建了组却再也管不到”的死角 | 隐藏空组（管理入口丢失）；单独的组管理弹窗（增加一层容器与状态） |
| 排序 | 分组按 sort_order；组内按下次续费日、再按名称 | 固定开支最关心“谁先扣”；自动排序无需维护拖拽状态 | 手动排序（需要额外字段与交互）；按金额（不符合续费时间直觉） |
| 分发条颜色 | 复用现有环形图的单色阶，按分组顺序取色 | 不新增品牌色/硬编码色，和资产分布、统计图表同一视觉语言 | 为每组存颜色（多一个字段和取色 UI）；随机色（不可预测） |
| 未来 7 天 | 含今天，截止第 6 天；只算使用中 | 与“未来 7 天”的日常理解一致，边界可测试 | 截止第 7 天（实际是 8 天）；只算明天起（漏掉今天待扣） |
| 年度预估 | 月合计 × 12 | 页面只管理月付，年度值是可解释的估算；文案明确“预估” | 按实际扣款日逐笔生成（本轮无账单）；不做年度（失去总量视角） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 第五个 Tab 在 320–440px 挤压品牌与操作区 | 高 | 两字文案 + 640px 以下仅图标 + 420px 以下 Tab 横向 padding 7px；320/360/400/420 断言无横向滚动、Tab 与操作区不相交、五个 Tab 中心点命中自身 |
| 删除分组误伤订阅 | 高 | 确认框写明“组内 N 项移至未分组”；数据库可空外键 + 集成测试断言订阅仍存在 |
| 扣款日 29–31 在短月不存在，日期漂移 | 中 | 推导时夹取当月最后一天；2 月、4 月、跨年、当天扣款各有纯函数用例 |
| 金额浮点累加导致合计与分组小计不一致 | 中 | 汇总只用 amount_cents；年度 = 月分 × 12；显示前统一除 100 |
| 页面在未登录时挂载，登录后不恢复 | 中 | 页面接收鉴权状态，true 时加载；登录成功用例覆盖 |
| 分组菜单/行菜单被滚动容器裁切 | 中 | 分组面板不设 overflow-hidden；沿用现有 OverflowMenu 的右对齐与页面级 Esc 关闭；Demo 检查首行与末行 |
| 空分组没有管理入口 | 中 | 「全部」视图保留空分组分区与操作菜单；筛选视图才隐藏空组 |
| 既有数据库升级失败或数据被重建 | 中 | 只新增 CREATE TABLE IF NOT EXISTS，不改旧表；在旧库夹具上执行 InitDB 两次并断言旧数据保留 |
| 订阅页与真实流水口径混淆 | 中 | 页面文案使用“固定开支 / 年度预估”，不写“已支出”；明确不自动记账 |
| 无 UI 测试框架导致交互回归 | 中 | 纯函数测试覆盖派生逻辑；后端集成测试覆盖 CRUD；浏览器手工复核多视口；不为此引入测试依赖 |
| 管理动作后本地状态与服务器不一致 | 低 | 每次成功变更后重新拉取分组与订阅；不做乐观更新；失败保留对话框与输入 |
| 分组重命名重复名 | 低 | 前端大小写不敏感预检；数据库 name COLLATE NOCASE UNIQUE 兜底并返回 400 |
| 首次加载失败与变更后刷新失败口径混淆 | 中 | 首次加载失败清空数据并显示重试面板；变更后刷新失败保留当前数据、显示同步提示与重试，两者走不同 load 模式 |

## 5. Phase 依赖关系

Phase 1 ──→ Phase 2 ──→ Phase 3 ──→ Phase 4 ──→ Phase 5

Phase 1 的接口字段决定 Phase 2 的类型；Phase 3 依赖契约与导航；Phase 4 依赖完整实现；Phase 5 依赖门禁结果。阶段内任务可以并行阅读，但写入保持串行。

## 6. Subagent 协同规划

| 阶段 | 上下文依赖 | 并行收益 | 执行主体 | 决策理由 |
|------|------------|----------|----------|----------|
| Phase 1：数据与 API | 强（既有迁移、鉴权、错误约定） | 无 | 主线 | 改动集中在同一条数据链路，拆分会增加契约对齐成本 |
| Phase 2：契约与导航 | 强（既有 API 客户端、App 状态、导航响应式） | 无 | 主线 | 差分小但跨文件，主线一次改完更稳 |
| Phase 3：页面与管理 | 强（同一页面的状态、弹层、菜单与视觉节奏） | 低 | 主线 | 视觉与交互互相牵制，隔离会话难以保持一致性 |
| Phase 4：测试与回归 | 中（需要知道最终字段与边界） | 低 | 主线 | 用例与实现边界同步推演更准确；测试量不足以抵消交接成本 |
| Phase 5：文档与归档 | 中（需汇总全部决策与门禁） | 低 | 主线 | 文档必须逐条对齐实际实现，主线书写更可靠 |

> **协同结论**：本轮是单页面、强串行、上下文高度耦合的交付，不派发 Subagent，全部由主线执行。
